# Website copy audit 001

**Date:** 2026-10-05
**Scope:** User-visible copy in public routes, account and contribution flows, shared listing templates, metadata, and site-wide error states.
**Changes:** Audit only. No website copy or behavior was changed.

This audit checks copy against the current repository implementation. The database inspection tool had no connection, so published agent/category records and their upstream repositories could not be checked individually. Findings about database-backed content refer to the rendering and fallback code, not to every live record. “Generic” means the wording is vague or conventional; it does not claim that a person or model authored it.

## Findings

### 1. P1 · Privacy policy says passwords never reach application code

The policy says: “Passwords are handled by that service and are not available to AgentHive application code.” The browser form stores the password in React state and passes it to Supabase Auth. Supabase handles authentication, but the statement that the password is unavailable to AgentHive application code is inaccurate as written.

**Evidence:** [privacy page](../../../app/privacy/page.tsx#L34), [AuthForm](../../../components/AuthForm.tsx#L13), [AuthForm submission](../../../components/AuthForm.tsx#L36)

**Why it matters:** This is a direct privacy assurance about what the application can access. Distinguish browser-side handling from whether AgentHive’s own servers receive or store the password.

**Relevant standard:** C-5, R-36.

### 2. P1 · Published freshness method does not match the trust-state logic

The methodology says repository metadata and verification dates are checked against a 180-day window and that stale records become “Needs review.” In the implementation, stale state uses `metadata_last_checked_at`, `last_commit_at`, or `metadata_is_stale`; `last_verified_date` is not part of that staleness calculation. Also, records with a verification score of 5 return “Verified” before the stale check runs.

**Evidence:** [methodology page](../../../app/methodology/page.tsx#L27), [trust-state logic](../../../lib/trust.ts#L21), [trust-state stale check](../../../lib/trust.ts#L27)

**Why it matters:** Visitors can be shown “Verified” even when the later freshness check would otherwise mark the record stale, and the documented review method does not describe the actual inputs.

**Relevant standard:** C-5, R-36.

### 3. P1 · “Best fit” can reward missing hardware information

The comparison score adds a point when `hardware_requirements` is empty, then names the highest-scoring entry “Best fit from recorded fields.” Missing information can therefore improve an agent’s score. The result also does not use a visitor’s hardware or preferences.

**Evidence:** [comparison scoring](../../../lib/compare.ts#L12), [comparison UI label](../../../app/compare/page.tsx#L43)

**Why it matters:** The label sounds like a meaningful recommendation, but the score is a completeness/recorded-field heuristic that can favor unknown requirements.

**Relevant standard:** C-5, R-36, R-38.

### 4. P1 · Legal pages visibly identify themselves as pre-launch drafts

The Privacy and Terms pages both show “Pre-launch review required.” They also say important details remain unconfirmed, including the operator’s legal identity, jurisdictions, providers, processing locations, retention periods, and legal terms.

**Evidence:** [privacy notice](../../../app/privacy/page.tsx#L18), [terms notice](../../../app/terms/page.tsx#L18), [privacy details still to confirm](../../../app/privacy/page.tsx#L84)

**Why it matters:** The notices are candid, not fabricated, but they tell visitors these pages are not final policies. Treat them as launch-readiness blockers if the site is being presented as a finished service.

**Relevant standard:** C-5, R-38.

### 5. HIGH · FAQ says every published entry has a last-verified date

The FAQ says every published entry includes a “last verified date.” The data normalizer uses “Not verified” when that value is absent, and the agent page omits the reviewed date in that state.

**Evidence:** [FAQ entry](../../../lib/faq.ts#L22), [missing-date fallback](../../../lib/data.ts#L73), [agent detail page](../../../app/agents/%5Bslug%5D/page.tsx)

**Why it matters:** The FAQ promises a date even though the UI explicitly supports entries without one.

**Relevant standard:** C-5, R-36.

### 6. HIGH · Join form says email is used only to reply

The form says an email is “Used only to reply to your application.” The Privacy page also says contact and contribution submissions are used “to review and respond,” so “only” understates the stated use.

**Evidence:** [JoinForm](../../../components/JoinForm.tsx#L60), [privacy purposes](../../../app/privacy/page.tsx#L73)

**Why it matters:** The form and privacy notice should describe the same handling.

**Relevant standard:** C-5, R-36.

### 7. HIGH · Join page promises a personal response that the workflow does not guarantee

The page says “Nilesh will review your note and get back to you by email.” The join flow submits the note, but the application cannot guarantee that a person will review it or reply by email. It also names one reviewer while the About page now presents the work in a collective “we” voice.

**Evidence:** [join page](../../../app/join/page.tsx#L18), [join submission form](../../../components/JoinForm.tsx)

**Why it matters:** This is a service promise rather than a description of what submission itself guarantees.

**Relevant standard:** C-5, R-38.

### 8. HIGH · FAQ overgeneralizes what local-model use means for privacy

The FAQ says local model support makes it easier to experiment “without sending prompts or files to a hosted provider.” That may be true of local inference, but it does not establish that a particular agent, tool, or configuration sends no prompts or files to any hosted service.

**Evidence:** [local-model FAQ](../../../lib/faq.ts#L46), [agent access information](../../../app/agents/%5Bslug%5D/page.tsx)

**Why it matters:** The assurance is broader than the per-agent network and tool-access information the directory records.

**Relevant standard:** C-5, R-36, R-38.

### 9. HIGH · Listing fallbacks sometimes invent details about missing documentation

When listing data is absent, the shared normalizer displays generic text. Some fallbacks make assumptions: the hardware message directs visitors to “pinned release documentation,” and troubleshooting directs them to an “issue tracker,” either of which may not exist. Other fallbacks plainly say information was not listed; those are transparent, but repeated boilerplate can still look like listing-specific guidance.

**Evidence:** [listing fallbacks](../../../lib/data.ts#L60), [category fallback](../../../lib/data.ts#L104), [agent detail rendering](../../../app/agents/%5Bslug%5D/page.tsx#L60)

**Why it matters:** Keep missing information explicit, and only point to a resource when the source record confirms it exists.

**Relevant standard:** C-1, C-5, R-38.

### 10. HIGH · Account-deletion confirmation omits contribution submissions

The confirmation says deletion removes saved agents. The deletion endpoint also calls a database function that deletes contribution submissions associated with the account or its exact email.

**Evidence:** [deletion confirmation](../../../components/DeleteAccountForm.tsx#L43), [deletion endpoint](../../../app/api/account/delete/route.ts#L32), [database deletion function](../../../supabase/023-admin-operations-and-related-agents.sql#L79)

**Why it matters:** Before an irreversible action, the confirmation should describe the other user data the operation deletes.

**Relevant standard:** C-5, R-38.

### 11. HIGH · “Open-source” is stated as a catalog-wide fact without a visible license check

Pages and metadata describe the catalog as a directory of open-source projects. The Terms page tells visitors to review each upstream project’s license, and the repository does not establish in the reviewed selection or display flow that every listed project has a checked, qualifying license. Individual database-backed entries could not be validated during this audit.

**Evidence:** [homepage metadata](../../../app/page.tsx#L13), [terms project/license guidance](../../../app/terms/page.tsx#L39), [search metadata](../../../app/search/page.tsx)

**Why it matters:** Either show what license evidence was checked, or use wording that does not imply a verified license status for every entry.

**Relevant standard:** C-5, R-36, R-38.

### 12. MEDIUM · Search and social metadata call agents “worth running”

The global title and social-card text say “Find AI agents worth running.” That is a value judgment about the projects and can read as endorsement, while the Terms and About pages explicitly say a listing is not an endorsement.

**Evidence:** [global metadata](../../../app/layout.tsx#L23), [Terms non-endorsement statement](../../../app/terms/page.tsx#L57), [About non-endorsement statement](../../../app/about/page.tsx#L121)

**Why it matters:** This phrase creates a first-impression claim that conflicts with the site’s stated limits.

**Relevant standard:** C-5, R-36.

### 13. P3 · Several homepage and signup lines are generic rather than informative

Examples include “Good projects get better together,” “A better way to evaluate,” “Keep the good ones in reach,” and “Start your collection.” The “better” claim has no stated comparison, while the other phrases could describe many unrelated products.

**Evidence:** [homepage invite](../../../app/page.tsx#L60), [signup page](../../../app/signup/page.tsx#L10)

**Why it matters:** These lines occupy prominent space without explaining a concrete AgentHive action or capability. This is an editorial quality issue, not proof that the wording is AI-generated.

**Relevant standard:** C-1, C-3.

### 14. P3 · Site-wide error copy assumes the visitor is viewing a directory listing

The 404 says “This page is not in the directory,” even though the 404 applies to any route. The generic error page tells visitors to “open the listing again,” even when the failed page may not be an agent listing.

**Evidence:** [404 page](../../../app/not-found.tsx#L7), [error page](../../../app/error.tsx#L4)

**Why it matters:** The recovery instruction should match the route-independent states those components handle.

**Relevant standard:** C-1, C-4.

## Copy that appears specific and useful

The search and filter descriptions, setup-step headings, source/version details, access and requirements labels, verification checklist, and stated verification limits are generally tied to visible product behavior. No site copy was changed as part of this audit.

## Not covered

The actual published agent and category descriptions, tags, setup commands, costs, license status, permissions, and linked upstream documentation remain unverified because the database connection was unavailable. Those records need an individual source check before making claims about their accuracy.
